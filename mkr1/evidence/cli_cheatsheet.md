## 📋 Перелік цільових запитань технічного інтерв'ю

### Питання #1 [Architecture & Async / Database]

**❓ Запитання:** У вас є FastAPI‑ендпоінт, який у асинхронному режимі читає дані з PostgreSQL (SQLAlchemy async) і потім робить HTTP‑запит до зовнішнього сервісу. Опишіть, як ви організуєте транзакцію, щоб у випадку помилки зовнішнього запиту дані не залишились у частково зафіксованому стані, і які механізми захисту від deadlock‑ів ви застосуєте.

**🎯 Що перевіряє лід:** *Перевірити розуміння асинхронних транзакцій, правильного використання контекстних менеджерів, rollback у випадку винятків, а також знання про рівень ізоляції, порядок блокувань і способи уникнути deadlock‑ів у високонавантажених сервісах.*

**🔑 Ключові тези для висвітлення:**
- Використання async with session.begin() / transaction
- Rollback у except block
- Обгортка зовнішнього запиту в try/except з timeout
- Встановлення рівня isolation READ COMMITTED або REPEATABLE READ
- Уникнення довгих блокувань за рахунок коротких транзакцій

### Питання #2 [Caching & Failure Handling]

**❓ Запитання:** Опишіть, як реалізувати патерн Cache‑Aside з захистом від Cache Stampede у FastAPI‑сервісі, який кешує результати дорогих SQL‑запитів у Redis. Які інструменти Redis ви використаєте, і як будете обробляти випадок, коли Redis недоступний?

**🎯 Що перевіряє лід:** *Оцінити знання про стратегії кешування, використання Redis LOCK/SETNX, алгоритм "early expiration" або "randomized TTL", а також підхід до деградації сервісу при відсутності кешу.*

**🔑 Ключові тези для висвітлення:**
- GET → спочатку перевірка кешу
- SETNX + короткий lock для запиту до БД
- Випадкове зменшення TTL для уникнення масових оновлень
- Fallback до DB, якщо Redis недоступний, і логування
- Використання redis-py async client

### Питання #3 [Docker & DevOps]

**❓ Запитання:** Поясніть, як побудувати multi‑stage Docker‑образ для FastAPI‑додатку, щоб мінімізувати розмір фінального образу, при цьому зберігши можливість запуску unit‑тестів у CI. Які файли та інструменти ви винесете у окремі стадії?

**🎯 Що перевіряє лід:** *Перевірити розуміння процесу оптимізації образу, розділення залежностей (build‑time vs runtime), використання .dockerignore та кешування шарів, а також здатність інтегрувати тестову стадію в CI‑pipeline.*

**🔑 Ключові тези для висвітлення:**
- Stage 1: python:3.11‑slim‑build, встановлення poetry/poetry install --no-dev
- Stage 2: копіювання лише .py файлів та встановлених wheel‑ів
- Stage 3 (optional): тестова стадія з pytest, використання --target test
- .dockerignore для виключення __pycache__, .git
- Використання --chown для зменшення прав

### Питання #4 [Testing]

**❓ Запитання:** Як би ви написали pytest‑тест для FastAPI‑ендпоінту, який залежить від Redis‑кешу та PostgreSQL, використовуючи fixtures, щоб забезпечити ізоляцію тестів і автоматичне очищення даних після кожного запуску?

**🎯 Що перевіряє лід:** *Оцінити вміння створювати складні fixtures, використовувати dependency_overrides у FastAPI, застосовувати транзакційний rollback або тестову базу, а також мокати/підключати Redis у тестовому режимі.*

**🔑 Ключові тези для висвітлення:**
- fixture scope='function' з async_engine.begin() та rollback
- override get_redis_dependency на fakeredis або тестовий інстанс
- client = TestClient(app) з overridden dependencies
- Використання @pytest.mark.asyncio
- Після тесту виклик redis.flushdb()

### Питання #5 [CI/CD & Resource Leak]

**❓ Запитання:** У GitLab CI ви маєте два job'и: build‑docker‑image та run‑tests. Які кроки додасте, щоб уникнути витоку ресурсів (наприклад, залишкових контейнерів чи підключень до DB) під час паралельного виконання job'ів, і як будете реагувати на випадкові "flaky" тести?

**🎯 Що перевіряє лід:** *Перевірити знання про правильне очищення Docker‑контейнерів, використання Docker‑in‑Docker з --rm, кешування шарів, а також стратегії retry, test‑sharding та моніторинг ресурсів у пайплайні.*

**🔑 Ключові тези для висвітлення:**
- docker run --rm у job'і
- docker system prune -f після build
- use of services:postgres, services:redis з healthcheck
- retry: 2 для flaky тестів
- parallel matrix для shard‑ованих тестів
- export CI_JOB_ID для унікальних назв контейнерів
